# Auth provider: Auth0, identity only

Scope: buyer and vendor users across all frontends and backends
Status: decided, not yet implemented

## 1. What was decided

Auth0 handles **authentication only**: signup and login (email and password, social, magic link), MFA and password resets, for both buyer and vendor users, in **one Auth0 tenant**. Authorization (which company, which role, what a person may do) stays in our own schema and Spring Boot code.

## 2. The reframe that settled it

The user's first uncertainty was how Auth0 would fit buyer companies and especially vendors. The answer was that the organization model is already built in our own schema:

- `buyer_companies` + `buyer_users` with roles admin, purchaser, approver, viewer
- `vendors` + `vendor_users` with roles admin, sales, support

So we don't need an auth provider's multi-tenant "Organizations" product, which is a paid Auth0 tier. We only need identity. That makes the cheaper scope enough.

## 3. Constraints that shaped the choice

| Constraint | Effect |
|------------|--------|
| Low cost | Identity-only scope, no paid Organizations feature |
| Solo founder, no team to run infrastructure | Managed provider. Self-hosted Keycloak was rejected as a whole IAM server to patch and operate |
| Many vendors are solo founders without their own domain or IT department | No mandatory domain verification and no mandatory SSO at signup. SSO is opt-in per organization later |

## 4. Options considered

| Option | Verdict |
|--------|---------|
| Auth0 | Chosen by the user. Industry-standard name, and first-class Machine-to-Machine (client-credentials) apps if the Python MCP service's auth later moves to the same provider |
| Clerk | Recommended for its Next.js integration and free tier, but not chosen |
| Keycloak (self-hosted) | Rejected because of the operating burden |
| Auth0 Organizations | Not needed; we model organizations ourselves |

## 5. How it plugs into the stack

- Next.js handles the Auth0 login flow and sends the access token to Spring Boot.
- Spring Boot validates Auth0 JWTs as an OAuth2 Resource Server (Spring Security, via the tenant's JWKS).
- The token's subject maps to a row in `buyer_users` or `vendor_users` through a new `auth_provider_id` column. That row gives the company and role.
- The Python MCP service doesn't go through Auth0 for now; it uses a shared API key with Spring Boot.

## 6. Schema impact

Designed but **not yet migrated** as of `isaas-database` `v1.0.0`:

- `auth_provider_id` on `buyer_users` and `vendor_users`
- `sso_connection_id` (nullable) on `buyer_companies` and `vendors`
- `buyer_join_requests` and `vendor_join_requests`

See `isaas-platform/architecture/auth-and-membership-2026-09-27-20-55.md`.

## 7. Next steps

- Migrate the schema additions above before building login in any backend.
- Later: SSO enterprise connections per organization, and possibly an M2M app for the Python services.
